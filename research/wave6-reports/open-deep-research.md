## Architecture in one paragraph (for orientation)

Current version (`src/open_deep_research/deep_researcher.py`): `clarify_with_user -> write_research_brief -> supervisor loop (ConductResearch -> N parallel researcher subgraphs) -> compress_research per researcher -> final_report_generation`. Researchers are plain tool-calling loops (search + `think_tool` + `ResearchComplete` sentinel) with iteration caps. Legacy A (`src/legacy/graph.py`): plan sections up front, then per-section `generate_queries -> search_web -> write_section -> section_grader (Feedback: pass/fail + follow-up queries) -> maybe re-search`, bounded by `max_search_depth=2`. Legacy B (`src/legacy/multi_agent.py`): supervisor/researcher agents with `Sections/Introduction/Conclusion/FinishReport` sentinel tools.

**There is NO token/cost metering anywhere.** Budgets are iteration counts only (`max_researcher_iterations=6`, `max_react_tool_calls=10`, `max_concurrent_research_units=5` — `src/open_deep_research/configuration.py:94-119`). Token limits are handled reactively (error classification + truncation), not proactively.

## Honest verdict on the FAR-Lab questions

**Does mid-run query adaptation help FAR-Lab's 82.3% arXiv zero-result problem?** Only the failure-driven half of it. ODR's loop adapts in two modes: (a) gap-driven — "I read the results, X is missing, search narrower" — which depends on having results to read and therefore does NOT engage in arXiv's zero-result regime; and (b) failure-driven — the tool's "No valid search results found, please try different queries" message (utils.py:126-127), which is exactly the trigger FAR-Lab lacks. ODR itself never solved arXiv zero-recall: its arXiv integration (legacy utils.py:577-731) paces rate limits but has no zero-result handling, and ODR's arXiv usage presumably suffered the same phrase-vs-coverage mismatch. So: a full agentic loop is NOT justified by this evidence; a **deterministic, bounded zero-result retry ladder** (shorten query / strip to 2-3 keywords / mutate) triggered per-target IS justified and is offline-verifiable against cached fixtures.

**Does the loop's value depend on general-web search?** Substantially, yes. The loop's compounding value in ODR comes from reading full webpage bodies (Tavily `raw_content` up to 50k chars, configuration.py:141-152) and re-narrowing against what was read — an option scholarly APIs (abstracts/metadata) mostly don't offer. What transfers to scholarly sources: (1) failure-driven reformulation, (2) per-source structured summaries of abstracts, (3) the clean-not-summarize merge contract, (4) bounded graded re-query. What does not transfer: broad-then-narrow reading strategy, supervisor parallel-researcher scaling, and the think_tool reflection cadence (its input is read content).
