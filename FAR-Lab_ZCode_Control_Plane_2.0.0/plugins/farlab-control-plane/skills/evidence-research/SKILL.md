# Evidence Research

## Objective

Produce decision-changing evidence, not a generic landscape summary.

## Protocol

1. State the exact decision/question and what evidence could change it.
2. Set freshness needs and source hierarchy. For consequential current claims prefer official docs/specs/source/repos/releases, primary papers/datasets and reproducible benchmarks.
3. Search by capability, failure mode, architecture primitive and scientific need rather than a fixed brand list.
4. Treat enumerated directions as discovery seeds, not a closed set. Explicitly consider adjacent extension ecosystems when relevant: libraries, SDKs, protocols, agent frameworks, Skills, plugins, MCP servers, hooks, tool suites, model gateways, workflow systems and scientific software.
5. Use independent query families for consequential decisions; avoid repeated near-duplicate searches.
6. For serious candidates inspect source, API/protocol, issues/releases, license, maintenance, security, extension model and real implementation path proportionally to decision importance.
7. Actively search contrary evidence, limitations, failure reports, stale assumptions, negative results and stronger alternatives.
8. Run an isolated spike/comparison when documentation cannot settle an architecture-changing question and execution is feasible.
9. Stop at **decision saturation**: additional independent searches mostly yield duplicates, clearly weaker candidates or already represented patterns.
10. Converge to `KEEP / ADOPT / ADAPT / EXTRACT / VENDOR / FORK / REBASE / BUILD / REPLACE / DELETE / DEFER / REJECT`, an experiment, or an explicit unresolved question.

For each material conclusion record: strongest evidence, conflicting evidence, evidence ceiling, uncertainty, implication, and the exact project decision/action it changes.

Never fabricate browsing, source inspection, release state, license, benchmarks, expert consensus or tool availability.
