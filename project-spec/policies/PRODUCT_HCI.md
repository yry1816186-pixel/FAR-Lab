# PRODUCT_HCI.md — 用户界面与人机体验细则

> 读取时机：任何用户接触面工作（Web / Desktop / CLI / 终端 / 报表 / 工件 / 可视化 / 可观测 UI）。Kernel 在根 AGENTS.md；本文件定义产品级设计流程与禁止清单。

## 1. 设计门禁（开始写代码前先回答）

任何界面不得直接堆组件。先回答：

1. 用户是谁？（角色、技术背景、使用频率）
2. 核心任务是什么？（Jobs To Be Done，一次会话完成什么）
3. 主要信息是什么？信息层级如何排列？
4. 关键操作是什么？最少步数完成？
5. 最危险状态是什么？（数据丢失、误操作、不可逆动作）
6. 用户需要比较什么？需要追溯什么？
7. 失败怎样发生、怎样恢复、怎样解释给用户？
8. 空态、加载态、权限不足态分别是什么内容？
9. 哪些科学事实必须可见（不确定性/反证/出处/执行模式/最弱环节）？哪些结论是机械判决、哪些是模型输出——界面如何不混淆二者？
10. 人工背书节点在哪（协议签名/测量记录/审批）？误触与未授权路径如何防（armed-confirm、actor 存档）？

输出（至少简版）：User Need → Task Flow → Information Hierarchy → Interaction → State → Implementation → Usability Verification。

## 1.1 成熟设计团队工作法

重要用户流程采用轻量但完整的设计闭环：

`Research/User Need -> JTBD/Task Analysis -> Information Architecture -> State/Interaction Model -> Wireframe/Prototype when useful -> Design System semantics -> Real Implementation -> Usability/Accessibility/Performance Verification`.

不要为形式产出大量设计稿；每一步只有在能改变真实交互/信息/风险决策时才保留产物。

UI 重构/新建一律走 **impeccable 技能闭环**（owner 指令 2026-08-26）：设计批评 → 实现 → impeccable detector + 多视口评审截图留档。不绕过、不手搓替代流程。

## 1.2 跨端、主题与语言

- Web/CLI 的核心任务与术语在 Windows、macOS、Linux 上保持一致；Linux 无图形环境至少能通过 CLI/远程 Web 完成核心任务。跨平台声明必须实测，不能凭框架宣传。
- 如果交付 Desktop wrapper，它只是一种运行表面，复用 canonical domain/application semantics，不建立第二套业务逻辑。
- 支持中英文本地化和 Light/Dark 时，使用语义 token/设计系统，不复制两套页面；长文本、时区、数字格式和主题对比度都要实测。
- Canvas/WebGL/复杂图形只在高密度科学可视化确有价值时采用，并提供可访问的文本/表格替代；禁止为了“高级感”加入。

## 2. 状态模型与 UI 真相（最高优先级）

- UI 状态必须映射真实系统状态：queued / running / paused / retrying / cancelled / partial / failed / completed 各有明确语义与来源。
- 不知道精确进度 → 不显示百分比；显示阶段与确定性事实（"第 3/5 步完成" vs "37%"）。
- 按钮没有真实能力 → 禁用或隐藏，禁止点击后无效果或假成功。
- 每个界面检查：真实 State / Action / Data / Error / Loading / Empty / Permission / Failure，缺失的态必须设计而非忽略。
- 长时间任务：显示当前阶段、可取消、可恢复、失败时状态不损坏；禁止"转圈然后什么都没发生"。

### 2.1 科研诚信表面（AOSSA 产品定义性要求）

- 执行模式（LIVE / OFFLINE / RECORDED / SYNTHETIC）在产出物与其入口常显；离线/回放路由的降级提示可见，不藏在文档里。
- 机械判决呈现为机械（预注册阈值 + 确定性规则可下钻查看）；模型输出不排版成客观事实；二者的视觉语言可区分。
- 不确定性、反证、最弱环节置信、exploratory/confirmatory 状态是可判读的一等内容；呈现层不得为美观抹平或弱化它们。
- 任何聚合可视（图/表/统计量）可下钻到 raw 数据或原始工件；下钻路径真实存在，不是装饰链接。
- 人工背书节点（协议签名/仪器记录/审批）使用 armed-confirm + actor 存档；伦理门 fail-closed 的呈现让"为什么被锁"可读，解锁路径给真实命令/动作。
- 缺席是一等态：无协议、无数据集、未形成问题模型都有诚实空态与成因说明，不渲染占位假象。

## 3. 用户与任务分析

- Persona 不是装饰：每个界面写清楚为谁、解决什么任务。
- 任务分析按频次与价值排序；高频路径必须最短。
- 术语全产品一致；Web / CLI / 报表同义异词 = 缺陷。

## 4. 信息架构与导航

- 导航反映任务模型，不反映代码结构。
- 导航深度由任务与信息复杂度证明；避免无必要层级，让高频关键任务可快速到达，不使用武断层级数字代替信息架构判断。
- 当数据规模/任务需要时提供搜索、过滤、排序、对比；不要给小数据集机械增加控件。证据/科研结果始终保留来源追溯。

## 5. 工作流与交互架构

- 每一步交互都有明确结果反馈（成功/失败/进行中）。
- 不可逆操作二次确认 + 说明后果；批量操作可撤销或可部分回滚。
- 表单：必填/校验/错误定位即时且明确；提交可重试不重复（幂等）。
- 键盘可达性：所有功能可键盘完成（TAB 顺序、快捷键、焦点可见）。

## 6. 错误 UX

- 错误信息：发生了什么 + 为什么（可理解）+ 用户能做什么 + 是否可重试/恢复。
- 失败不得破坏状态；失败后返回的界面必须反映真实状态。
- 错误分级：可恢复提示、需干预警告、阻断性错误；禁止所有错误一个样式。

## 7. 可视化

- 图表必须由真实数据驱动；装饰性图表 = 禁止。
- 图表类型匹配数据语义（对比/趋势/分布/关系）；轴、单位、来源、时间戳等元信息在适用时必须清楚，不能制造无法解释的视觉编码。
- 可追溯：任何可视结果可下钻到原始证据。

## 8. 命令体验（CLI / 终端）

- CLI：交互使用默认人类可读，自动化提供稳定 `--json`/机器可读模式；退出码语义明确，`--help` 完整。
- 长命令可中断、可恢复、可重入（checkpoint/resume）；输出真实阶段/状态，只有运行时确知时才给确定进度。
- 终端彩色输出必须同时支持禁用；信息密度优先于装饰。

## 9. 报表与工件

- 报表 = 决策支持：结论在前，证据在后，来源可查。
- 导出工件（ReproducibilityBundle 等）自带清单与校验（provenance receipt），可独立复现。

## 10. 视觉系统

- 成熟设计靠：typography、hierarchy、spacing、composition、restraint、semantic color、information density。
- 语义色只表达语义（成功/失败/警告/信息），不表达装饰。
- 动效服务理解（状态转移、层级变化），无意义动画禁止。
- 禁止清单（AI Dashboard 拜物教）：紫蓝渐变、发光、玻璃拟态、满屏 Card、假神经网络、科技粒子、装饰性图表、fake terminal、无意义动画、为截图美化而破坏真实产品。

## 11. 可访问性与国际化

- 对比度、字号、点击目标尺寸达标；语义化标签；屏幕阅读器可读。
- 国际化：文案不硬编码；日期/数字/时区处理正确；布局适应文字长度。
- 响应式：关键任务在窄屏可完成，不追求像素级一致。

## 12. 性能体验

- 首屏与关键交互建立经过测量的性能预算；大数据量按实际模式采用分页、虚拟化、聚合或渐进加载等合适策略。
- 慢操作显示真实阶段、已耗时、可取消/恢复与阻塞原因；只有基于测量且足够可靠时才显示 ETA，禁止编造预期时间。

## 13. 验收

- UX 验收 = 设计走查 + 真实任务试用 + 可访问性扫描；记录结果。
- "好看"不是验收标准；"用户能正确、快速、无误解地完成任务"才是。
- Web 表面常驻门禁：zh/en 全量对等（dict.ts 单事实源，EN 泄漏 = e2e 失败）、
  375px 零横向溢出、axe critical/serious = 0、键盘可完成核心旅程——这四条
  是回归门禁，不随需求波动。
